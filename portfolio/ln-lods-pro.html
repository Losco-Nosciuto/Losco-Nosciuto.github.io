LN LODs Pro — a commercial add-on born from a pipeline problem

A Blender add-on that makes the LOD count in Blender match the MSFS 2024 exporter, and lets you test the transitions before export.

On this page

Context The problem Why I wrote it How the method changed The technical hurdles Inside the viewer Result Limits What I learned

Context

In Microsoft Flight Simulator 2024 a model is exported with several LODs; the simulator picks one according to screen coverage. The thresholds live in the model's XML, and the exporter writes them from its own vertex count. That count is not the number Blender shows: the exporter splits seams, normals, colours and tangents, and merges objects before counting.

The SDK's exporter is the reference. The add-on does not replace it: it calculates the same count, writes the values into the LOD groups and keeps the standard pipeline as the only path.

The problem

A model could look correct in Blender and pop in the simulator, because the threshold was calculated on a different vertex count. The only way to find out was to export, open the sim, fly to the right distance and look. Then go back, change a number and repeat.

I wanted the loop inside Blender: see the count the exporter will see, see the coverage at a given distance, and test the transition before writing the files.

Why I wrote it

I work as an independent developer and partner in the MSFS ecosystem; I use the SDK and the exporter every day. At the time I could not find a tool that counted vertices the way the exporter does and let me test the result before export. So I wrote it, and I kept using it.

It was not a weekend script. The first version was a way to avoid a manual count; the Pro line added the viewer, non-destructive operators and a maintenance history. The decision to spend months on it was taken because the work it removed was repetitive and measurable.

How the method changed

The tool started in 2023 and grew in phases. What changed is not only the code: it is the way I write it.

  1. 2023

    ChatGPT and Notepad++

    First working version. Copy, paste, run, fix; no version control and no plan.

  2. 2023

    VS Code and Git

    The project becomes a codebase: history, diffs, a structure that can survive a pause.

  3. 2024

    Agents

    Plan and audit files, explicit context, human review. The agent accelerates; the domain knowledge stays mine.

  4. 2026

    Suite and rework

    The add-on becomes the first module of a suite of MSFS tools; the agent workspace behind it is public.

The workspace is open source: six OpenCode agents, a verified knowledge cache and an installer. It is not a magic prompt; it is a discipline made of plans, audits and checks.

The technical hurdles

  1. 01

    Counting vertices like the exporter

    Seams, split normals, colours, tangents and merged objects: the count has to follow the same rules as the MSFS 2024 exporter, not Blender's statistics panel.

  2. 02

    Performance on large scenes

    Vectorised numpy where it matters, a BMesh fallback where it does not, and a cache keyed on object identity to avoid recounting the same mesh.

  3. 03

    Testing LODs without exporting

    Bounding sphere, coverage as radius divided by distance, clamped to the same range the simulator uses. The viewer shows the thresholds before the exporter runs.

  4. 04

    Instant LOD switching

    Modifiers are baked when testing mode is entered, so the LOD change is immediate and the scene stays comparable.

  5. 05

    Non-destructive operators

    Overlays, lens, visibility and undo state are saved and restored. Testing a LOD must not leave the file changed.

  6. 06

    Integration with the exporter

    Values are written into the LOD groups, with rounding and margin, and the standard export path remains the only one.

The viewer, in code

The part that pays for itself: the viewport decides which LOD collection stays visible, using the same vertical screen size the simulator uses.

Coverage comes from the bounding sphere of the whole model and from the live viewport FOV, not from what is visible on screen. MSFS 2024 does not clamp at the sphere surface, so the ratio is r / (d · tan(fov/2)), capped at 10 and multiplied by 100; the 2020 legacy path uses min(r/d × 1000, 1000).

# ln_lod_screen.py
def screen_size_percent(radius, distance, fov_y, lod_factor=1.0):
    """MSFS 2024 vertical screen size, in percent (0..1000)."""
    if radius <= 0.0 or fov_y <= 0.0:
        return 0.0
    d = max(distance, 0.001)
    half_tan = math.tan(fov_y / 2.0)
    ratio = (radius * lod_factor) / (d * half_tan)
    return min(ratio, 10.0) * 100.0

Then the viewer keeps one coverage value per model — the same for every LOD in the group — picks the first LOD whose threshold is met, and hides all the others. The choice is a pure-Python function, so it can be tested without Blender.

# ln_testing_state.py
def choose_lod_index(entries):
    """First LOD whose coverage reaches its threshold, else the last one."""
    if not entries:
        return None
    for index, (threshold, coverage) in enumerate(entries):
        if coverage >= threshold:
            return index
    return len(entries) - 1
# ln_lod_viewer.py
def _update_group(self, context, group_item):
    if not group_item.enabled:
        return

    # Highest detail first: thresholds descending, LOD number as tiebreaker.
    ordered = sorted(
        group_item.lods,
        key=lambda lod: (-lod.screen_threshold, lod.lod_number),
    )
    if not ordered:
        return

    # One coverage per model, as the simulator does: the bounding sphere of
    # the whole model decides the screen size for every LOD.
    center, radius = get_group_bounding_sphere(group_item)
    coverage = compute_msfs_coverage(center, radius, self._live_region_3d())

    entries = [(lod.screen_threshold, coverage) for lod in ordered]
    index = ln_testing_state.choose_lod_index(entries)
    if index is None:
        return

    chosen = ordered[index]
    for sub in ordered:
        coll = bpy.data.collections.get(sub.collection_name)
        if coll:
            coll.hide_viewport = (sub != chosen)

How the numbers were measured

Hundreds of models, including testers during the 3.x pre-release. The vertex count is 1:1 with the exporter because the add-on uses the same export and triangulation engine, based on Khronos glTF. The margin slider is a fallback for Asobo updates, not an error compensation.

Time saved depends on the model: 15 minutes to 1 hour of LOD debug for a simple model; complex models with sub-models or multiple meshes, each with its own LODs, can reach hours.

Version 1.6 was the first public release: free, with no LOD debugger. The 3.x line brought the first Pro iteration and the viewer with its testing mode. The 4.x line standardized the split: Pro is the free base plus the Pro modules; strip those modules and it still works as the free version.

It is sold on Gumroad and Superhive, is GPL-licensed and ships its source with the purchase. The 4.x line is in rework for the suite.

Limits

The add-on depends on the exporter's internals. A change in the SDK can change the count, and the add-on has to follow. It also depends on Blender's API: a new version can break an operator or a panel.

The margin slider is not a correction for an intrinsic error: it is a buffer for the window between an Asobo update and the package update.

Edge cases remain: non-manifold geometry, heavy modifier stacks, instancing. The tool minimises the risk; it does not eliminate it. The design choice is to make the failure visible before export, not to promise a perfect count on every scene.

What I learned

The domain knowledge is yours; the agent accelerates it. A model can propose a solution, but it cannot know why the exporter counts a seam twice. That is the part you bring.

Maintenance is the real cost. The code you do not touch is the code that stays correct; the rest is a sequence of small decisions that have to remain legible six months later.
