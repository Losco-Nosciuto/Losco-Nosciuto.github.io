How I work

A tool is worth writing when the work it removes is worth the time it costs. It can be a two-hour ToDo app or a suite that takes months: the criterion is not size, it is the efficiency left behind. Code is a means, not the result.

With agents I work like this: I listen to the advice, then I verify it. If the proposed solution does not match the numbers, either the numbers or the solution is wrong, and it is worth finding out which. On the DayZ launcher the agent first handed me a list of 2,000 servers, then an inflated 105,000. I checked two other launchers: they sat between 40,000 and 60,000. I rebuilt the sweep, the filters and the server-farm rules until the number held — and it is still not perfect.

Knowing your limits is a strength, not a weakness. In the LODs plugin the final vertex count is exact because it replicates the MSFS 2024 export pipeline, which starts from the Khronos glTF exporter. A DayZ launcher is different: server farms change method, server names are human variables that cannot be used as an absolute filter, and a rule like "full server + queue = authentic" rejects good servers just because they are full at that moment. The design choice is to minimize collateral damage, not to guarantee 100%.

Prompt engineering

A prompt is not a magic formula: it is a directive. You cannot write about something you know nothing about without doing research. Knowing the structure of what you are building, and the basics of how the tool works, makes a prompt closer to a detailed technical specification — and it works every time. Better.

Objective
Limit token waste and get more done in fewer passes.
Constraints
Project-specific, with hard limits and clear boundaries at all times.
Context
Audit and plan files always up to date. Tell the agent, precisely, what to write and when: not only in code, but in the textual structure of the project.
Examples
When technical knowledge is incomplete and research does not close the gap, examples give the agent context in pieces. Few, but important. The agent is an extension of the mind.
Iteration
Every cycle ends with plan and audit updated: the next step starts from there, not from chat memory.
# Blender add-on — implement a feature already specified
Role        Blender add-on developer
Objective   Implement the NLA-strip iteration feature described in plan.md
Context     MSFS 2024 exporter pipeline. plan.md holds the spec, the official
            documentation links and the decisions taken so far; audit.md holds the
            change history. Read them before writing; do not restate them.
Constraints - Extend bpy.types.NlaStrip properties with the fields in plan.md.
              No parallel list for the UI.
            - Replace the second export button with a monkey patch that intercepts
              the XML creation and edits it: the standard MSFS exporter pipeline
              stays the only path.
            - Create the folder structure only; write no files yet.
            - If a requirement is unclear, ask before writing.
Outputs     Code changes, plus plan.md and audit.md updated in the same pass
Criterion   The standard exporter produces the edited XML with no extra manual
            step; plan and audit reflect every change.
